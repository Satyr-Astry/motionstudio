# 导入裁剪：非透明包围盒（PSD + 位图）— 2026-10

对象：`app/shell/import-file.mjs`（唯一实现文件）、`tests/import-file.test.mjs`（新增用例）。
本文是这一轮的四项验收取证记录：三条解码路径、PNG 也裁、`alphaBounds` 性能、去掉 `layer.__trim`。
所有真机数字来自 Chromium（Edge + CDP，`http://127.0.0.1:8900/app` 的静态服务），基准数字来自 node。

## 结论

1. 三条解码路径（`ImageData + createImageBitmap` / 临时 canvas + `putImageData` / 裸像素描述）在改后**仍然逐项给出同一个矩形**，且 `ImageData` 构造器拿到的就是**裁后**缓冲（`data.length === w*h*4` 全部成立）。见 §2。
2. 位图（PNG/JPEG/WebP）走同一套规则裁剪：132×92 带 6px 留白 → 120×80，原点补 `+6/+6`；裁后画面与不裁**逐像素相同**（`maxDiff = 0`）。见 §3。
3. 8000×8000 单层的 `alphaBounds`：满内容层 97.5ms → **66µs**；有留白的层 95.6ms → 37.2ms；全透明 64.9ms → 35.8ms。见 §4。
4. 图层对象上不再出现 `__trim`：`psdLayerImage` 改为返回 `{image, trim}`，调用方拿不到半个结果。见 §1。

### 1.1 `alphaBounds`：两条路径，同一个答案

```js
const ALPHA_MASK = (() => {
    const probe = new Uint32Array(new Uint8ClampedArray([0, 0, 0, 1]).buffer);
    return probe[0] === 1 ? 0x000000ff : 0xff000000;   // 探字节序，不写死 0xff000000
})();

export function alphaBounds(pixels, width, height) {
    const w = intOr(width, 0);
    const h = intOr(height, 0);
    if (!w || !h || !pixels) return null;
    if (byteSizeOf(pixels) < w * h * 4) return null;
    const words = wordsOf(pixels);
    if (words.length < w * h) return null;

    if (edgeIsOpaque(words, w, h)) return { x: 0, y: 0, w, h };   // O(2w+2h)

    let x0 = w, y0 = h, x1 = -1, y1 = -1;
    for (let y = 0; y < h; y += 1) {
        const base = y * w;
        let acc = 0;
        for (let x = 0; x < w; x += 1) acc |= words[base + x];    // 整行按位或
        if ((acc & ALPHA_MASK) === 0) continue;                   // 整行透明 → 跳过
        let lo = 0;
        while (lo < w && (words[base + lo] & ALPHA_MASK) === 0) lo += 1;
        if (lo >= w) continue;
        let hi = w - 1;
        while (hi > lo && (words[base + hi] & ALPHA_MASK) === 0) hi -= 1;
        if (lo < x0) x0 = lo;
        if (hi > x1) x1 = hi;
        if (y < y0) y0 = y;
        if (y > y1) y1 = y;
    }
    if (x1 < x0 || y1 < y0) return null;
    return { x: x0, y: y0, w: x1 - x0 + 1, h: y1 - y0 + 1 };
}
```

两个坑，都补了守卫：

- `byteSizeOf` 而不是 `pixels.length`。`Uint32Array` 的 `length` 是元素数，拿它比 `w*h*4` 会把合法缓冲判短；`byteLength` 才对。
- `wordsOf` 对更宽的视图按**字节**对待：`new Uint8ClampedArray(u32view)` 会按元素截断成 1/4 长度，必须是 `new Uint8ClampedArray(v.buffer, v.byteOffset, v.byteLength).slice()`。非 4 字节对齐的 `byteOffset` 再对齐一次（`Uint32Array` 构造器对未对齐偏移直接抛 `RangeError`）。

不做跳步采样。跳过像素有机会把 1 像素宽的内容漏掉，包围盒算小 → 内容被切边。宁慢不切。

改前的 `layer.__trim = { dx, dy }` 有两个毛病：`layer` 是 `psd.mjs` 的产物、会流到调用方手里，私有字段挂上去谁都能读到；位图和偏移能被分开拿走，只传位图不传偏移就静默错位。现在两者打包返回，`splitLayerImage` 只认「同时有 `image` 和 `trim` 两个自有键」的容器，注入 `makeImage` 返回裸位图的老用法一个字节都不用改（`trim` 为 `null` ≡ 没裁）。

### 1.3 位图裁剪

```js
const IMAGE_TRIM_MAX_PIXELS = 4096 * 4096;

function trimBitmap(bitmap, opts) {
    if (o.trim === false) return { skipped: 'off' };
    if (w * h > IMAGE_TRIM_MAX_PIXELS) return { skipped: 'big' };
    const pixels = bitmapPixels(bitmap);
    if (!pixels) return { skipped: 'nopixels' };
    const box = alphaBounds(pixels, pixels.width, pixels.height);
    if (!box) return { skipped: 'clear' };                    // 全透明：没内容可裁
    if (整张相等) return { skipped: 'full' };
    const image = cropBitmap(bitmap, box, pixels);             // putImageData，整数偏移
    if (!image) return { skipped: 'nobitmap' };
    return { image, box };
}
```

`imageToObject` 的居中量仍按**原图**尺寸算，再补 `dx/dy`：

```js
const x = cx + dx;   // cx = round((canvasW - w) / 2)，w 是原图宽
const y = cy + dy;
```

按裁后尺寸重新居中会让内容在导入瞬间平移 —— 与 PSD 路径「裁掉的只是透明的纸」的约定相反，不做。

`report` 保留原有的 `width/height`（**原图**尺寸，既有语义不改），新增 `trimmed`、`contentWidth`、`contentHeight`、`trimSkipped`。

`IMAGE_TRIM_MAX_PIXELS = 4096 × 4096` 是 2026-10 定下的上限，**不放宽**：读像素要再拷一份整图，峰值内存比一次慢导入更伤。超限时 `report` 只记 `trimSkipped: 'big'`，**不报错、不中断导入**：`imageToObject` 仍返回 `ok: true`，`trimmed` 为 `false`，位图与坐标完全按原图走。同理 `'nopixels'`（读不到像素）、`'clear'`（全透明）、`'full'`（本来就没留白）、`'off'`（调用方传 `trim: false`）也都是「没裁」而不是「失败」——这五种都不该打断用户的导入。

### 2.1 `ImageData` 拿到的是裁后缓冲

在页面里包一层 `window.createImageBitmap`，记录构造器实参：

```
{width:28, height:15, dataLen:1680, consistent:true}
{width:20, height:16, dataLen:1280, consistent:true}
{width:28, height:22, dataLen:2464, consistent:true}
{width:40, height:30, dataLen:4800, consistent:true}
{width:927, height:439, dataLen:1627812, consistent:true}
```

`consistent` 判据是 `data.length === width * height * 4`。**这一条是必要的但不是充分的**，所以补了反向验证：故意构造长度不符的 `ImageData`，Chromium 抛
`IndexSizeError: Failed to construct 'ImageData': The input data length is no…`（尺寸偏大、偏小两种错法都抛）。既然正向调用没抛，缓冲与尺寸就是严格配对的。

### 2.3 与任务描述的偏差（如实记录）

- **路径②在 Chromium 里走不到**：`createImageBitmap` 对 `ImageData` 正常接受，只有把它打成抛错桩才会落到临时 canvas 分支。这条分支的真实用户是「`createImageBitmap` 被拒的环境」，真机上只能靠桩触发，上面的 28×15/20×16 等读数是桩强制下的结果。
- 三条路径的**几何**完全一致，但**位图类型**不同（`ImageBitmap` / `HTMLCanvasElement` / 普通对象）。下游只消费 `.width`/`.height` 和 `drawImage`，所以这不成问题；若哪天有人往 `cel.image` 上要 `.close()`（`ImageBitmap` 专有），路径②③会立刻暴露。
- commit message 里的样本名写作 `offset-layers-raw`，`fixtures` 里的实际文件叫 **`offset-raw.psd`**。

## 3. 位图（PNG/JPEG/WebP）也裁

132×92 的 PNG（内容 120×80 居中、四周 6px 透明），真机走 `imageToObject` 真实解码：

```
origSize  [132, 92]
gotSize   [120, 80]   ctor = HTMLCanvasElement
report    width 132 / height 92（原图）  x 6 / y 6  trimmed true  contentWidth 120  contentHeight 80
          trimSkipped '' 
```

裁后画面 vs 不裁参照的同一区域：`maxDiff=0  channelsOff=0/38400`。

### 3.1 低 alpha 的量化误差来自解码，不来自裁剪

这一条必须说清楚，否则容易被当成裁剪的副作用。样本 alpha 取 4..35（预乘最容易被压坏的那段），三组对照：

| 对照 | 全不透明内容 | 低 alpha 内容 |
| --- | --- | --- |
| 不裁（今天的实际情况）vs PNG 原始像素 | maxDiff 0 | **maxDiff 32**，27449/38400 通道有差 |
| 裁剪后 vs PNG 原始像素 | maxDiff 0 | **maxDiff 32**，27449/38400 通道有差 |
| 裁剪后 vs 不裁参照 | maxDiff 0 | **maxDiff 0** |

低 alpha 像素的颜色误差（最大 32/255）在**不裁的时候一模一样**：canvas 内部按预乘存 8 位，`drawImage` 写进去就已经丢了精度。裁剪路径多出来的那一步 `getImageData → putImageData`（`cropBitmap`）**没有再加任何误差**（第三行 0）。换言之这是浏览器位图解码的固有代价，与本次改动无关。

代价换来的是：位图读像素要多做一次整图 `getImageData` 拷贝。所以加了 `IMAGE_TRIM_MAX_PIXELS = 4096 × 4096` 上限，超过就 `skipped:'big'` 保持原图——宁可带着留白，也不把一次导入变成几百 MB 的峰值。

## 4. `alphaBounds` 性能

8000×8000 = 6400 万像素（244 MiB 缓冲），改前实现从 `e09bdf0` 原样拷进基准脚本，每组取 7 次中位数。脚本 `ms-view/w1-bench.mjs`。

| 场景 | 改前 | 改后 | 倍数 | 结果一致 |
| --- | --- | --- | --- | --- |
| 满层 `alpha=255`（最常见） | 97.5ms | **66µs** | 1475× | ✓ |
| 四周留白 100px | 95.6ms | 37.2ms | 3× | ✓ |
| 全透明 | 64.9ms | 35.8ms | 2× | ✓ |
| 满层 `alpha=1`（此前认为最坏） | 97.1ms | **63µs** | 1532× | ✓ |

读数口径：单次测量会被 JIT 首次编译和 244 MiB 缓冲的冷缓存带偏（首次满层读到过 697µs），所以每组预热 1 次再取 7 次中位数。

真实的形态分布决定了这个表的意义：

- **满内容层**是绝大多数（整层填色、从背景派生的层、画满的画布）。边界抽查是唯一能做到亚毫秒的形态，这部分从 100ms 级降到微秒级。
- **有留白的层**必须扫完才能定边界——「包围盒不是整张」这个结论无法从局部推断。这里只把常数压下来（整字读 4 字节/次、整行短路、两端收缩），3 倍是天花板附近，不假装能跳过扫描。绝对数字仍与像素数成正比：4000×4000 的留白层大约 9ms。
- 原以为「半透明 `alpha=1` 每点都要判」是最坏情况，实际它边界全不透明，走快路径，反而最快。
