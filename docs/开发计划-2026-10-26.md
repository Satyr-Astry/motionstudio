## 1. 第 24 批 —— 效果参数全线动画化（强度 / RGB / 偏移）

### 1.1 现状（已验证的事实）

- 效果定义在 `app/paint/effects.mjs`：`EFFECT_DEFS` 五项 —— `blur`（`amount` 模糊半径）、`glow`（`amount` + `color`）、`shadow`（`dx`/`dy`/`amount` + `color`）、`adjust`（`brightness`/`contrast`/`saturate`/`hue`）、`outline`（`amount` + `color`）；参数构造器 `num(key,label,min,max,step,def)`（`:21`）与 `rgb(key,label,def)`（`:26`，带 `color: true`）。
- **数值参数已经能动画**：写入口 `app/shell/commands.mjs:53 setEffectParam`（有关键帧就在当前时间打帧，否则改静态值）、`:71 keyEffectParam`（◆ 建/补一个关键帧）、`:89 clearEffectParam`（把曲线当值烘成静态值再删轨）；读入口 `app/core/evaluator.mjs:326` → `effectAt(e, ltime)`。ctx 已在 `app/shell/app.mjs:107-109`、`:930` 暴露这三个方法。
- **三个真缺口**：
  1. **颜色不能动画**：`effectAt`（`app/paint/effects.mjs:245`）只遍历 `e.tracks` 的数值轨道，`:253-254` 明确 `if (spec && spec.color) continue;`；`app/editors/prop-object.mjs:498` 注释也写着「颜色没有标量可插值，整条回写」。
  2. **曲线编辑器看不到效果通道**：`app/editors/curve-geo.mjs:32 SCALAR_CHANNELS` 只有 8 个变换字段，`:90` 的通道全集 = `SCALAR_CHANNELS` + 网格顶点通道；`:129 isChannelField(chId)` 只认 `app/core/transform.mjs:28 TRACK_FIELDS`，`:126` 注释写明「非 TRACK_FIELDS 的通道 core 的 `setChannelKey` 会直接抛 TypeError」。→ 效果参数虽然能打帧，但曲线面板里既看不见也编辑不了。
  3. **效果没有稳定 id**：`layer.effects` 是数组、按 `fxIndex` 定位，`app/shell/commands.mjs` 所有效果命令都靠 index。删除/上移效果会让 index 位移，任何以 `fx0` 命名的通道都会指错效果。

1. 给 `glow.color` 在 t=0 打红、t=1 打蓝，播放到 t=0.5 时渲染出的外发光颜色在两者之间（取图像中心外围 1px 采样的 RGB 三分量都介于两端之间）。

### 1.4 待定（需要用户拍板，实施前一次问清）

- **颜色轨存法**：三条数值轨（`color.r/g/b`，直接复用现有 Track 全套，代价=曲线里多两行）还是单条颜色轨（存十六进制串，代价=新的插值/关键帧类型、序列化升级）。
- **插值色彩空间**：sRGB 直插（简单、会发灰发暗）还是 Oklab（好看、要多写 100 行色彩转换）。默认建议 sRGB 直插 + 后续可换。
- **「shader」的含义**：现在效果是 Canvas2D 后处理（`app/paint/effects.mjs` 的 `applyEffect` 一类），不是 GPU shader；若你要真 shader（WebGL/WebGPU 管线），那是**另一条独立路线**（第 25 批的 B 选项），工作量 ≈ 新建一条渲染管线 + 现有 5 个效果重写，风险高，建议单独评估。

## 3. 第 26 批 —— 网格内部拖拽（还原 Klecks 手感）

### 3.1 现状（用户的抱怨点，已定位）

- 命中层 `app/editors/canvas-input.mjs:35` 有 `kind:'lattice'`，但只有**点中顶点**才进 warp 拖拽（`:271-274` `ctx.setSelection({ id, mode:'warp', vertex })`）；点图像内部而没点中顶点 → 落到 `move` 分支 = **改对象位置**。
- 网格数学：`app/core/lattice.mjs` —— `(cols+1)×(rows+1)` 个顶点，每顶点存**像素偏移** `pts`；`latticeOffset(lat,u,v)`（`:114`）是**每个 cell 内部双线性**，`latticePoint`（`:130`）、`cellQuad`（`:136`）；渲染与命中按 cell 三角形细分，与双线性严格一致。

### 3.2 Klecks 的做法（已读到精确实现，作为规格）

`E:\dev\klecks\src\app\script\klecks\transform\ffd.ts:317 warpLatticeViaPoint(paramCoordinate, target, lattice)`：

- 对每个控制点算 Bernstein 基 `w = bernstein(n,j,s) * bernstein(m,i,t)`；
- 距离斜坡 `strength = max(0, 1 - paramDist / influenceRadius)`，`influenceRadius = 1/3`（注释：靠试出来的手感，让变形局部化）；
- 对「比拖拽点更靠外」的控制点再乘 `edgeFalloff = 0.5`（注释：越小边缘越不容易翻折）；
- `sumWeightsSq = Σ w²·strength`，每个控制点位移 `= 拖拽位移 × (w / sumWeightsSq) × strength`；
- **不变量**：`evalFFD(paramCoordinate, updatedLattice) === target` 精确成立（拖拽点严格跟手）。
- 调用方：`ui/easel/tools/easel-select.ts:314`（Klecks 的 warp 工具里，拖内部就是走这条）。

差异：Klecks 用 **Bernstein 曲面 + 控制点绝对坐标**；我们用 **per-cell 双线性 + 顶点偏移**。

### 3.3 两条路（建议先 A）

| 方案 | 做法 | 代价 | 风险 |
| --- | --- | --- | --- |
| **A 局部双线性逆解（推荐先做）** | 新增纯函数 `latticeDragAt(lat, u, v, dx, dy, { radius = 1 })`：取拖动点所在 cell 的四角双线性权重 `µ`，解 `Σ µ_i²` 归一后把位移分给 4 个角点（保证拖拽点精确跟手），再按距离把残余分给相邻一圈顶点做平滑；`radius` 以 cell 为单位 | 只动 `app/core/lattice.mjs` + `canvas-input.mjs` 的命中分支 + 测试 | 大位移跨 cell 时不如 Bernstein 平滑；折角出现在 cell 边界 |
| **B 升级为 Bernstein 曲面** | 顶点改绝对坐标、`latticeOffset` 换成 Bernstein 求值、渲染三角形细分与命中全部重写 | `lattice.mjs` 全改 + 渲染路径改 + 既有 9 组网格测试重写 | 与现有「每 cell 双线性与三角形严格一致」的保证冲突，回归面大 |

建议：**先 A**（一周内可上线，用户立刻能用），把 B 记为「若 A 观感不够再上」。

### 3.4 交互规格

- 网格模式下按下时命中顺序：顶点（现有）→ **图像内部（新增，双线性 uv 落在 [0,1] 且该点 alpha > 0）** → 对象本体（只有不在网格模式或点在图像外才走 move）。
- 拖动中显示「影响圈」（半径 = `radius` 个 cell 的柔和圆），并实时预览网格；松手才 `setDoc` 一次、一条撤销。
- 修饰键：`Alt` = 老行为（拖内部 = 移动对象），给习惯旧操作的路径留出口；`Esc` 取消本次拖动。
- 网格顶点拖动（现有）保持不变。

### 3.5 验收

1. 纯函数测试：`latticeDragAt` 在拖拽点处位移精确等于目标（误差 < 1e-9）、四角权重和为 1、`radius` 边界不产生 NaN、位移幅值被 `MAX_STEP` 夹住。
2. 真机：40×30 纹理、2×2 网格，从内部 `(0.5,0.5)` 拖 `(+20,+10)` → 采样网格点位移、图像中心像素偏移 `≈(+20,+10)`、对象 `transform.keys[0].state.x/y` **不变**（与「改对象位置」区分）。
3. 从图像外拖同一对象 → 仍走移动（老行为）。
4. 一次拖动一条撤销；`Alt` 反向行为可用。

| B 允许边播边拖 | 拖动期间让时间轴跳过「时间档」刷新（`refresh-plan` 加一档 `frozen`），并冻结 `playLoop` 的 `state.time` 写入 | 手感炫，但「播到一半拖键」语义歧义大（键在时间轴上滑走的同时播放头也在跑），且要改刷新分级与播放循环两处 |

采用 A，但 D 的细节仍要处理：播放被自动暂停时**必须有提示**，否则用户会以为播放崩了。

### 8.3 改动面

| 子项 | 文件 | 做法 |
| --- | --- | --- |
| 31a 统一入口 | `app/shell/doc-state.mjs`（或 `app/shell/app.mjs` 的 ctx 层） | 新增 `pauseForEdit(reason)`：`playing` 为真时 `setPlaying(false)` + `notify`，返回是否发生了暂停；所有「写时间相关字段」的入口先调它 |
| 31b 关键帧拖动 | `app/editors/timeline-keys.mjs` | `onKfDown` 首行 `deps.pauseForEdit('关键帧')`；拖动中若仍侦测到 `playing`（极端竞态）则放弃本次拖动并提示 |
| 31c 参数与属性写入 | `app/shell/commands.mjs`、`app/editors/prop-object.mjs`、`app/editors/prop-textures.mjs` | `setEffectParam` / 变换字段 / 纹理尺寸等「会打帧或改时间语义」的入口统一调 `pauseForEdit`；纯静态编辑（改名字、改颜色静态值）不触发 |
| 31d 播放中选/删的守卫 | `app/editors/timeline-keys.mjs`、`app/shell/app.mjs` | 播放中 `Delete` 删关键帧同样先暂停；播放中框选允许（只读操作，不打断播放） |
| 31e 编辑器视觉 | `app/styles/panels.css`、`app/editors/timeline-paint.mjs` | 播放中 ⏸→▶ 图标、状态栏「播放中」段；暂停由编辑触发时时间轴上闪一下内联提示（`notify` 之外的可视反馈） |
| 31f 探针与测试 | `tests/playback-guard.test.mjs`（新）、`ms-view/expr-play-edit.txt` | `pauseForEdit` 纯逻辑（playing 真/假两态、重复调用只提示一次）；真机：播放中按住关键帧后连续采样 `state.time` |

### 8.4 验收判据（真机读数）

1. 播放中点住关键帧 → 同一帧内 `playing === false`，出现提示；`state.time` 停在按下那一刻（与拖动前读数差 < 1 帧）。
2. 拖动 500ms 期间每 50ms 采样 `state.time`：10 次读数**完全相同**（这就是「预览不被拍回」的可测形式），且被拖节点 `style.left` 随鼠标单调变化。
3. 松手后：文档里该键时间 = 预览值（误差 < `T_EPS`）、一条撤销、`undo` 回到原位。
4. 播放中拖属性滑杆 500ms → 只新增 **1** 个关键帧（读数：`track.keys.length` 增量），不是每帧一个；若取证发现当前实现确实撒一排，这条就是本批主修复项。
5. 纯静态编辑（改对象名、改静态颜色）在播放中**不**触发暂停。
6. 播放中 `Delete` 删选中关键帧 → 先暂停、再删除、一条撤销。

### 8.5 风险

- 「编辑即暂停」是**行为变更**，习惯边播边调的用户会觉得被打断 → 提示文案要给出原因，并在设置里留一个「播放中编辑时自动暂停」开关（默认开），便于改回去。
- 若第 4 条取证成立（真在撒帧），修法要在 `addKey` 层加「同一手势内同一轨道只保留最新一帧」，属于数据层改动，要额外回归 `tests/curve-write-mode.test.mjs` 与 undo 合并语义。

## 10. 第 33 批 —— 导出：通道补齐

### 10.1 缺口

| 缺口 | 现状证据 | 影响 |
| --- | --- | --- |
| 精灵图不分张 | `buildSpritesheet` 只建一张 canvas（`app/shell/spritesheet.mjs:198`） | 大动画（如 200 帧 1024²）会撞 Chromium 的单边/总面积上限，`toDataURL` 直接失败或返回空白，且**没有预检** |
| 精灵图不去空白 | `sheetLayout:117` 只按「格宽高 + gap」排 | 大量透明边距白白占图集，显存与包体浪费 |
| 帧表只有自家格式 | `SHEET_FORMAT = 'motionstudio-spritesheet'`（`:30`） | 不能直接喂 Phaser / Godot / Unity / TexturePacker |
| 只能整段导出 | 见 9.1 | 没有「导出当前帧 PNG」，也没有「复制到剪贴板」 |
| 只有 PNG | `toDataURL('image/png')` | 照片类纹理或大图序列体积降不下来（无 JPEG/WebP 选项） |

### 10.2 做法

| 子项 | 内容 |
| --- | --- |
| 33a 分张与预检 | `sheetLayout` 增加 `maxTextureSize`（默认 4096，可调），超限时输出**多张** `sheet-1.png/sheet-2.png…`，帧表 `sheets:[{file,w,h}]` 记录归属；导出前先算总格数并**预检**，超限直接给出「需要 N 张图集」的提示而不是失败 |
| 33b 去空白（trim） | 复用 `app/shell/import-file.mjs` 的 `alphaBounds`/`cropBitmap`（导入链路已在用）对每格裁到内容包围盒，帧表新增 `sx/sy/sw/sh`（原图偏移）与 `trimmed:true`；默认开，可关 |
| 33c 引擎格式 | 帧表除自带格式外，多给一份 **Phaser 3 JSON Hash**（最普及、字段最直白），并留一个 `format` 选项位；Godot/Unity 的图集导入差异大，本轮不做，文档写清为什么 |
| 33d 单帧与剪贴板 | 新命令 `导出当前帧 PNG`（走 `saveBinary`）与 `复制当前帧到剪贴板`（`navigator.clipboard.write([new ClipboardItem('image/png', blob)])`，Electron 里可用） |
| 33e 格式选择 | PNG 序列 / 精灵图增加 `png | webp | jpeg`（`canvas.toDataURL(type, quality)`；JPEG 强制不透明底，透明时提示） |

### 10.3 验收判据

1. 200 帧 × 1024² 的工程导出：产出 `sheet-1…N.png`，每张 `≤ maxTextureSize`，帧表 `sheets[]` 与文件一一对应；总格数 = 帧数。
2. 带 30% 透明边距的帧：`trimmed` 后单格面积显著下降（读数给改前/改后字节数与面积），并且回放到引擎里位置正确（`sx/sy` 偏移把内容放回原处）。
3. Phaser JSON Hash 交给一个最小 Phaser 场景能显示（或至少字段与本机 Phaser 文档逐条比对通过）。
4. 「复制当前帧到剪贴板」后粘贴到画图工具能粘出图像（真机截图）。
5. 导出 WebP 序列：体积比 PNG 小且透明保留；导出 JPEG：透明被填成对话框里选的底色，不静默变黑。

## 11. 第 34 批 —— 导出：视频离线编码

### 11.1 现状与代价

- `recordVideo`（`app/shell/project-io.mjs:1214`）用 `cv.captureStream(0)` + `MediaRecorder`，每帧之间**按真实时间等待**（`:1208-1209` 注释自陈）。
- 后果：①1 分钟动画要录 1 分钟；②窗口切后台会被 Chromium 节流，录出来变慢/掉帧（`exportVideo` 里专门 `flash('开始录制 WebM，请保持窗口在前台…')`）；③透明通道未开（VP9 alpha 未启用，透明导出后变黑）；④只有 WebM，没有 MP4；⑤码率/质量只有 `videoBitrate`（`app/shell/video-plan.mjs:69`）一个旋钮。

### 11.2 做法（先验证再投入）

| 步骤 | 内容 |
| --- | --- |
| 34a 可行性验证（**先做，一天内**） | 最小探针：`typeof VideoEncoder === 'function'`、`VideoEncoder.isConfigSupported({codec:'vp09.00.10.08', alpha:'keep'})`、`vp8`、`avc1.42001f` 各自支持情况；同样验 `VideoFrame` from `canvas`。拿不到就**停在这里**，把结论写进文档，不做 34b–34d |
| 34b 离线逐帧编码 | 用 `VideoEncoder` + `VideoFrame(canvas, {timestamp})` 按「采样时刻」喂帧，**不等墙上时钟**；容器用 `webm-muxer`（或最小自写 WebM 封装），输出 `ArrayBuffer` → 复用 `ms:save-binary` |
| 34c alpha 与 MP4 | 34a 若支持 `alpha:'keep'` → 透明导出（VP9 + alpha）；MP4 若 `avc1` 可用则加容器选项，否则文档写清「Chromium 的 MP4 需要平台硬编码器，本机不支持」 |
| 34d GIF（可选） | 量化调色板 + 逐帧写 GIF（无第三方依赖的话自写 LZW 约 200 行），只在「≤256 色 / ≤10 秒」时提供，超出时提示体积 |

### 11.3 验收判据

1. 3 秒动画的导出耗时 < 5 秒（对比现在的 ≈3 秒 + 编码开销），且**窗口可以切到后台**、结果帧数不变。
2. 导出的 WebM 用 `ffprobe`/Chromium 回放：`nb_frames` = 期望帧数、时长误差 < 1 帧。
3. 透明工程导出：`vp9` + alpha 下回放背景透明（或明确提示「本机不支持 alpha，已填底色」）。
4. 34a 的探针结果表写进 `docs/导出栈-2026-10.md`，作为「做/不做 34c、34d」的依据。

### 11.4 风险

- `VideoEncoder` 在 Electron 40（Chromium 130 左右）里存在，但**编码器实现随平台**：Windows 上 vp9 软件编码可用性、`alpha:'keep'` 支持都要实测；不支持就得退回 MediaRecorder 并保留现有提示。
- 自写 WebM 封装容易在 `Cluster/Duration` 上出错（时长字段缺失导致播放器显示 0:00），所以优先用成熟的 muxer 库；若坚持零依赖，先做「能被 Chrome 播」的最小实现再补全。
