# 纹理尺寸：按内容裁剪与重设画布（2026-10）

用户报的缺口（原话）：**「画板的对象尺寸适配无法使用，当我擦除冗余部分时点击适配后无法去除透明通道尺寸到合适尺寸，以及无法在画板中调节对象尺寸，比方说我应该可以拓展画板扩大对象尺寸」**。

这份文档回答三件事：为什么「适配」不是他以为的裁剪、两条模式各自怎么推导坐标、以及真机读数。

## 1. 「适配」不是裁剪

画板工具栏的「适配」调用的是 `app/editors/board.mjs:255 fit()`，它改的是**视图相机**（`engine.setView` 那一层），效果的 title 自己写着「缩放到刚好放下这张纹理（0 键）」。也就是说它做的是「让这张图铺满可视区」，**像素一个都没动**。

用户真正想要的是两件不同的事：

1. 擦掉一片之后，把整张纹理**裁**到剩下内容的最小矩形（PSD 导入时那次 `alphaBounds` 干的是同一件事，但那只在导入时发生一次）；
2. 把纹理**画布**改成别的尺寸 —— 变大时可以往四周留白继续画，变小时按九宫格选保留哪一块。

这两件事本轮做成了一组纯函数（`app/paint/trim.mjs`）加一条文档命令（`ctx.resizeTexture`）。UI 由另一路（`task-30`）接，按下面的契约调即可。

## 2. 契约

```js
ctx.resizeTexture(objId, opts) -> boolean
  opts = { mode: 'trim' }
       | { mode: 'resize', width, height, align }   // align 缺省 'c'
```

- 只替换**当前时刻那一张纹理**的图像；同一对象别的纹理、别的纹理都不动。
- 一次操作 = **一条撤销**：图像与 transform 在同一个 `setDoc` 里落地。
- 返回 `false` 时文档一定没被改过，并且已经给了人话提示。

失败路径的文案（这几条是真机抓的原文）：

| 情况 | 提示 | 返回 |
| --- | --- | --- |
| 纹理全透明 | `这张纹理是全透明的，没有内容可裁` | false |
| 四周本来就没有透明区域 | `这张纹理四周没有多余的透明区域` | false |
| 尺寸不是 1–4096 | `尺寸必须是 1–4096 之间的数字` | false |
| 尺寸与当前相同 | `尺寸没有变化` | false |
| 读不出像素（既没有 `getContext` 也画不出来） | `这张纹理没有可读取的像素` | false |

## 3. 坐标推导（最容易写反的地方）

目标只有一条：**像素内容在世界坐标里不动**。

设对象变换里当前生效的关键帧 `x/y = (X, Y)`，且这一帧没有旋转缩放（有旋转缩放时下面的推导仍然成立，因为补偿量是在**对象局部坐标**里加减的）。

### trim

旧图 `W×H`，内容包围盒 `box = {x: bx, y: by, w: bw, h: bh}`。

- 旧图里内容左上角那个像素，世界坐标是 `(X + bx, Y + by)`；
- 裁完之后它变成新图的 `(0, 0)`，所以新图的 `X'` 必须满足 `X' + 0 = X + bx`：

```
X' = X + box.x
Y' = Y + box.y
```

**加**，不是减。

### resize

新画布 `nw×nh`，九宫格对齐给出的落位偏移是 `(ox, oy)`（`alignOffset` 算的就是它：`ox = round((nw - W) * fx)`，`fx` 由 `align` 决定，`nw > W` 时为正、`nw < W` 时为负）。

内容整体在画布上平移了 `(ox, oy)`，要让它在世界里不动：

```
X' = X - ox
Y' = Y - oy
```

**减**。

### 一条能抓出写反的断言

`tests/resize-texture.test.mjs` 里对九宫格每一档都算了「旧图左上角的世界坐标」在前后是否相等：

```js
worldOf(X', Y', ox, oy) === worldOf(X, Y, 0, 0)
```

写成 `+ox` 的话这条会立刻挂。

## 4. 真机读数

环境：`8900` 只读副本 + CDP `9334`，1280×800；用户自己开着的那个窗口（43117）全程没碰。

造样本：40×30 的 `OffscreenCanvas`，红色矩形画在 `(10, 8)` 起 12×10 的位置。

| 步骤 | 图像尺寸 | 关键帧 x/y | 提示 |
| --- | --- | --- | --- |
| 初始 | 40 × 30 | 0 / 0 | — |
| `contentBounds` | — | — | `{x:10, y:8, w:12, h:10}` |
| `{mode:'trim'}` → true | **12 × 10** | **10 / 8** | `已裁到内容：12 × 10` |
| `undo()` 一次 | **40 × 30** | **0 / 0** | — |
| `{mode:'resize', width:80, height:60, align:'c'}` → true | **80 × 60** | **−20 / −15** | `纹理尺寸改为 80 × 60` |
| 全透明纹理 `{mode:'trim'}` → false | 不变 | 不变 | `这张纹理是全透明的，没有内容可裁` |

`errors: 0`。

几个数字对得上：`alignOffset(40,30,80,60,'c') = {ox:20, oy:15}`，所以 `0−20 = −20`、`0−15 = −15`；撤销一次就把**图像和坐标一起**带回去了（不是只回一半）。

**两个坑都出在「怎么给对象挂一张图」上，跟命令本身无关。**

第一个：**挂图必须走 `DM.setImageAt(obj, t, canvas)`**。直接把 `cels[0].image` 赋成画布**不会进 `doc.drawings` 资产表** —— `imageAt()` 读的是 key 上的 `drawing` 再查资产表，`cels` 只是 `projectCels()` 投出来的投影。改投影等于没挂图，`readRgba(imageAt(...))` 拿到 null，于是所有读像素的命令都走「这张纹理没有可读取的像素」那条分支，看起来像命令坏了。（独立复验时踩到的，30×20 样本、`trim` 一直返回 false。）

第二个：第一版脚本在 `setImageAt` 之后只等了 300ms 就调 `resizeTexture`，而 `setDoc` 的自动合并窗口是 `DOC_GESTURE_MS = 700ms`，于是两次写入被合并成一条撤销记录 —— `undo()` 一次直接退回到「对象还没有图」的状态，看起来像「撤销把图弄丢了」。间隔拉到 900ms 之后读数就正常了。**用户手点两次不会这么快，但写测试的人要注意。**

## 5. 边界与实现取舍

- **上限 4096**：`clampTextureSize` 拒绝 `0`、`4097`、`NaN`、`Infinity`、`null`、`''`。选 4096 不是新定的规矩 —— 仓库里 `core/doc-model.mjs` 的尺寸出清、画板 `BOARD_MAX`、属性输入框 `input.max` 三处都是 4096，这里跟着走。
- **不做夹取**：用户输 9999 时告警，而不是悄悄改成 4096。「悄悄地修成看起来合法」比报错更难查。
- **`-0` 归一**：`alignOffset` 在 `nw === W` 时会算出 `Math.round(-0)`，它不影响计算但会污染 `deepEqual` 与序列化，所以在实现里归一成 `0`。
- **不假设有 `getContext`**：纹理可能是导入的 `ImageBitmap`（`alpha.4` 的 `pixelAlpha` 就是因为假设有 `getContext` 而永远读成 alpha 0）。`readRgba` 先试 `getContext`，失败就画一次到 `OffscreenCanvas` 再读；写回统一走 `createSurface`（优先 `OffscreenCanvas`，退化 `<canvas>`）。
- **alpha 判定 `>= 8`**：与取色器 `pixelHex(d, alphaMin)` 的 `alphaMin = 8` 同口径 —— 肉眼看不出来的像素算空气。注意这与 `hitTest` 的 `alpha > 8`（严格大于）**语义不同**，两边刻意没统一（命中要「宁可选中」，裁剪要「真有内容」）。
