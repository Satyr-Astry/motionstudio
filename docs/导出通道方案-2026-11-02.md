# 导出通道方案（2026-11-02）

> 用户方向第四条的原话是「程序的可用性还不够高，它服务于什么还不明确」。定位已经落成
> 「面向独立游戏与前端演示的 2D 角色与特效动画工具」（README 与 `docs/骨骼动画方案-2026-11-02.md` 都写了），
> 但**定位要靠导出兑现**：用户做完一段动画，得能直接拿去用。这份文档只谈这一件事。
>
> 现状一句话：能导出**帧序列**（png/webp/jpeg）、**精灵图**（自有格式 + Phaser 3 Hash）、**WebM 视频**。
> 缺的是「一张能直接发出去的透明动图」和「引擎能直接吃的帧表」。

## 1. 现状（实测）

- `app/core/export-options.mjs:33` `FORMATS = ['png', 'webp', 'jpeg']`；`:36` `ENGINES = ['own', 'phaser', 'both']`。
- `app/shell/spritesheet.mjs` 产 `motionstudio-spritesheet` v1（`frames[]` 带秒、`duration`）与 `phaserJSON()`（Phaser 3 JSON Hash，`frame_0000` 系列）。
- WebM 走**实时录制**（`project-io.mjs` 的 `exportVideo`），不是离线编码——这意味着导出时长 = 演示时长，且掉帧不可控。
- 三条导出命令都走对话框 + PNG 分片写（`main.js:155-185`），精灵图会自动分张并按内容裁剪。

## 2. 缺口与优先级

| 缺口 | 谁在等它 | 成本 | 价值 |
| --- | --- | --- | --- |
| 引擎帧表（Aseprite / TexturePacker / Godot / Unity） | 独立游戏美术 | **极低**（几十行纯数据映射） | 高——现在的自有格式没人能直接吃 |
| 透明动图（GIF / APNG） | 前端与设计、内容作者 | 中（要自己写编码器） | 高——这是「发出去就能看」的唯一形态 |
| 导出预设 | 所有人 | 低（一张表 + 一个字段） | 中——把「格式+引擎+缩放+裁剪+fps」打包，少点六次 |
| 离线视频编码（WebCodecs） | — | 高 | 低（计划 §13 已列本轮不做） |

## 3. 四项方案

### 3.1 引擎帧表：加 Aseprite JSON — ✅ 已发 `0.5.0-alpha.26`

Aseprite 的 JSON 格式事实上是**通用交换格式**：Aseprite 自己、TexturePacker、Godot（`SpriteFrames` 导入插件）、Love2D、Unity 的第三方导入器都能读。加一个模板就同时打开四条工具链。

- 落点：`app/shell/spritesheet.mjs` 新增 `asepriteJSON(sheet, opts)`，与 `phaserJSON()` 并列。
- 形状：`{ frames: [{ filename, frame:{x,y,w,h}, rotated:false, trimmed:false, spriteSourceSize:{x,y,w,h}, sourceSize:{w,h}, duration }], meta:{ app, version, image, format:'RGBA8888', size:{w,h}, scale, frameTags:[{name:'default',from,to,direction:'forward'}] } }`。
- `ENGINES` 扩成 `['own', 'phaser', 'aseprite', 'both']`（`both` 语义保持「自家 + 另选一种」，需要时再加 `all`）。
- 验收：把导出物丢进 Aseprite 的「Import Sprite Sheet」能对上帧数与时长；`tests/` 里钉 `frames[0].frame.x === 0`、`meta.size` 等于图集尺寸、`duration` 单位是毫秒（**Aseprite 用毫秒，本项目内部用秒——这是唯一必须换算的地方，也是唯一容易错的地方**）。

### 3.2 透明动图：GIF — ✅ 已发 `0.5.0-alpha.26`

浏览器 `canvas.toBlob('image/png')` 能给每帧 PNG，但**没有任何浏览器 API 能直接产 GIF**。要 GIF 就得自己写：

1. 逐帧 `getImageData` → 量化到 ≤256 色（中位切分或八叉树；建议**全局调色板 + Floyd–Steinberg 可选抖动**，局部调色板会让文件大一倍）。
2. LZW 压缩（GIF 的变体，约 120 行）+ 块写出（`GCE` 里设透明索引与 disposal）。
3. 循环扩展（`NETSCAPE2.0`）才能无限循环。

- 落点：新建 `app/core/gif.mjs`（纯 core，不碰 DOM，输入是 `ImageData` 数组 + 每帧延时毫秒），约 350 行；`project-io.mjs` 加 `exportGif()` 走已有的 `ipc.saveBinaryChecked`。
- 三条已知限制（要写进 UI 提示，别让用户以为 bug）：**GIF 的透明只有 1 位**（半透明边缘会变硬边）、256 色对渐变不友好、文件比 WebM 大。
- 验收：导出的 GIF 能在 Windows 照片、浏览器、Discord 里循环播放；透明区边缘无黑边；`tests/gif.test.mjs` 钉「2×2 纯色 2 帧」的字节流（GIF89a 头、`NETSCAPE2.0`、LZW 最小码宽），这是唯一能在 node 里断言的地方。

### 3.3 APNG — ✅ 已发 `0.5.0-alpha.27`

APNG = 普通 PNG + `acTL`/`fcTL`/`fdAT` 三个块，浏览器与 Windows 照片都支持，**全 alpha、体积极小**。麻烦在于要自己拼 PNG：

- 压缩可以用浏览器的 `CompressionStream('deflate-raw')`（Chromium 自带，拿到的是裸 deflate 字节，PNG 要的 zlib 头 `0x78 0x9C` + adler32 要自己补）。
- 落点：新建 `app/core/apng.mjs`（约 400 行）+ `exportApng()`。
- 风险：`CompressionStream` 在 Electron 40 可用（Chromium 132），但**核仓要在浏览器里也能跑**，所以要有「不支持就降级提示」的分支，不能假设它一定在。
- 建议：**先做 GIF**（无平台依赖、一定跑得通），APNG 作为后续增强。

### 3.4 导出预设 — ✅ 已发 `0.5.0-alpha.26`

`EXPORT_DEFAULTS` 加 `preset` 字段，`PRESETS` 表四项：

| 预设 | 格式 | 引擎 | 缩放 | 裁剪 | fps | 场景 |
| --- | --- | --- | --- | --- | --- | --- |
| `engine` | png | aseprite | 1 | 是 | 跟随文档 | 丢进引擎 |
| `web` | webp | own | 1 | 是 | 跟随文档 | 网页 `<img>`/CSS 精灵 |
| `chat` | gif | — | 0.5 | 是 | 12 | 发聊天 |
| `print` | png | — | 2 | 否 | 60 | 高分辨率帧序列 |

- 落点：`export-options.mjs` 加 `PRESETS` 与 `presetOf(name)`；对话框顶部加一排预设按钮（选预设 = 一次写满下游选项，用户仍可手改）。
- 关键约束：**预设只是初值，不是模式**——选完再改任何一项都不许被「改回去」。

## 4. 建议顺序

1. **3.1 + 3.4**（半天）：纯数据映射 + 一张表，零风险，立刻让「丢进引擎能用」成立。
2. **3.2 GIF**（一天）：唯一能给非开发者看的形态；写之前先做调色板量化，编码器可以后补。
3. **3.3 APNG**（一天半）：等 GIF 的量化模块稳定后复用。

## 5. 不做什么

- **WebCodecs 离线编码**：计划 §13 已列不做，实时录制够用。
- **MP4/H.264**：要许可证与编码器，不做。
- **Spine / DragonBones 导出**：属于骨骼 P4 的互操作，先把自有格式与矩阵导出做对。
- **序列帧打包成 zip**：`openFolder` 在浏览器里没有对应 API，zip 又要把整批图读进内存——收益低于成本。
