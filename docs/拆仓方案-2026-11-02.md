> 本文件是**计划稿**，不是已完成的事实记录。所有「现在是什么样」都带 `文件:行号`；所有「拆完该是什么样」都是待执行建议。查不实的写「未实测」。本文只新增这一个文件，不动代码/配置/索引。落地时按 [docs/README.md:65-69](README.md) 的规矩在主账本各加一行——那两步留给执行阶段。

## 1. 为什么拆：缝只有一处

本仓同时装着「核」（渲染层，能当静态网站跑）与「壳」（Electron 主进程 + 打包）。

- 核：`app/`（102 个 `.mjs`：core 26 / editors 29 / i18n 14 / paint 12 / shell 21）、`tests/`（100 个 `*.test.mjs`）、`docs/`（39 个 `.md`）、`_check-static.mjs`、`_check-syntax.mjs`、`_check-i18n.mjs`、`tools-smoke.cjs`。
- 壳：`main.js`（422 行）、`preload.js`（40 行）、`package.json` 的 `main`/`devDependencies`/`build`/`start`/`dist`（`package.json:6`、`:20-23`、`:42-81`、`:9`、`:17-18`）、`tools-pack.mjs`（70 行）、`dist/`。

两半只经一条缝接触：`app/shell/ipc.mjs` 的 `bridge()` 读 `globalThis.window.motionAPI`（`ipc.mjs:51-52`）。任务书说「唯一接触桌面能力的行是 `ipc.mjs:19`」——`:19` 是注释行（七通道表在 `ipc.mjs:12-19`），**真正的读取点是 `ipc.mjs:51`**。施工时 grep 这一行。

核侧调用点共 14 行：9 处桥方法调用 + 5 处 `ipc.available()` 守卫，分布在 `app/shell/project-io.mjs`（`:237` `:240` `:276` `:300` `:342` `:408` `:411` `:439` `:465` `:718` `:723` `:759` `:1769`）与 `app/shell/import-file.mjs:1007`。`README.md:93` 说「nine call sites」，指的就是那 9 处方法调用。

拆得开的四条证据：

1. `app/` 本身就是站点根：`app/index.html` 只有 9 个相对 `<link>`（`index.html:7-19`）+ 2 个相对 module script（`index.html:31-32`），CSP 是 `default-src 'self'`（`index.html:5`）。
2. `app/**/*.mjs` 里没有任何主机名/端口/协议：实测 `grep -E "127\.0\.0\.1|43117|43812|https?://"` 在 `app/` 下 **0 命中**。URL 只在壳里（`main.js:277`、`tools-smoke.cjs:128`）。
3. 无 preload 也能跑：`tools-smoke.cjs:112-117` 的窗口 `contextIsolation:true, nodeIntegration:false` 且不挂 preload；`:172-177` 判据要求 `window.motionAPI` 必须是 `undefined`、canvas ≥1、topbar 按钮 ≥5、状态栏非空，跑满 15 个编辑器。
4. 网页桥已落地：`app/shell/bridge-web.mjs:249-259` 在没有 `window.motionAPI` 时装六路降级实现，`:263` 模块求值即装，`index.html:31` 把它排在 `app.mjs` 前。

## 2. 第 1 题：目录与仓库形态

**结论**：核仓 `motionstudio`（就是现在这个仓库，`main.js`/`preload.js`/`tools-pack.mjs`/`dist/` 移出工作树），壳仓 `motionstudio-desktop`（新仓），壳用 **git submodule** 取核，挂载点是壳仓的 **`core/`**。

**挂载点为什么不是 `app/`**：核仓的站点根是**核仓自己的 `app/`**（`app/index.html`），而壳的 `main.js:10` 期望 `__dirname/app/index.html`，`:277` 再 `loadURL('http://127.0.0.1:'+port+'/index.html')`。若把 submodule 挂到壳仓 `app/`，站点根会变成 `app/app/index.html`，主进程的静态服务直接 404 白屏。挂 `core/` 后只需改 `main.js:10` **一行**（`path.join(__dirname,'core','app')`），并且打包时只列 `core/app/**/*`，天然把核仓的 `tests/`、`docs/`、`_check-*.mjs` 排除在安装包外——挂 `app/` 的方案得反过来逐条写 `!app/tests/**` 之类的排除项。

```
motionstudio/                      motionstudio-desktop/
  app/               ← 站点根        core/  ← submodule → motionstudio（gitlink）
  tests/                            main.js        （:10 改为 __dirname/core/app）
  docs/                             preload.js
  _check-static.mjs                 tools-pack.mjs
  _check-syntax.mjs                 test/channels.test.mjs   （新建，第 5 节）
  _check-i18n.mjs                   package.json
  tools-smoke.cjs                   package-lock.json
  tools-serve.mjs    （新建）        README.md
  package.json                      CHANGELOG.md            （壳自己的）
  package-lock.json                 .gitignore
  README.md / README.zh-Hans.md     dist/                   （.gitignore 掉）
  CHANGELOG.md
  LICENSE
  .gitignore
```

挂 `core/` 后两处路径随之改：`main.js:10`（`APP_DIR`）、`tools-pack.mjs:30` 的 `copyDir(root/app → resources/app/app)` 改为 `copyDir(root/core/app → resources/app/app)`。`main.js:11` 的 `INDEX` 是**死常量**（全文未使用，路径由 `:35-41` 的 `resolveFile` 拼），可顺手删掉。

`tools-smoke.cjs` 留在**核仓根**：它把 `app/` 当 `__dirname/app` 取（`tools-smoke.cjs:25`），放核仓根正好对上；只有一份源码，壳仓不复制。

**为什么是 submodule**（对 npm 产物、下载 zip 的取舍）：

| | submodule（推荐） | npm 产物 | 下载 zip |
| --- | --- | --- | --- |
| 发版锁定 | gitlink 锁 commit，`git submodule status` 一眼看出 | lockfile 锁版本号，够用 | 无锁定，靠文件名/URL |
| 本地改核代码 | `cd app` 就是完整工作树，改完在核仓提交、壳仓 bump 指针 | 要 `npm link`/`npm pack` 本地装，改一行重发布一次 | 改完就丢，下次同步被覆盖 |
| 需要什么基建 | 无 | 核要能发 npm 包，且要包内容白名单 | 要归档服务器 + 校验脚本 |
| 主要代价 | 使用者要记得 `--recursive` | 双份构建产物 | 无历史、无 diff |

否决点：核仓现在是 `private: true`（`package.json:4`），改成可发布包得先决定「核要不要上 npm」——那是另一个决策，而 npm 包也带不走历史与 tag。submodule 零基建。

**场景 A：本地要改核代码**

```bash
git clone --recursive https://github.com/Satyr-Astry/motionstudio-desktop.git
cd motionstudio-desktop/core && git switch -c fix/xxx  # 核仓完整工作树，在这里跑 npm test / npm run check
git commit -am "fix: …" && git push
cd .. && git add core && git commit -m "chore(core): bump core to <sha>"
```

开发循环：壳仓 `npm start` → Electron 起本地静态服务 → 从 `core/app` 读（`main.js:10` 改成 `APP_DIR = path.join(__dirname,'core','app')`，就这一行）。

**场景 B：只打包发版**：`git clone --recursive` → `npm ci` → `npm run dist`。不碰核仓，gitlink 指向已验证的核 commit。核仓发「网页版」时也不需要壳仓：把 `app/` 整目录推给任何静态托管。

> ⚠️ **未实测**：electron-builder 26 在 `core/` 是 gitlink 时对 `files:["core/app/**/*"]`（对应现在 `package.json:54` 的 `app/**/*`）的收集行为。预期「按路径 glob 收集，与是否 gitlink 无关」，但**必须在拆完第一次 `npm run dist:dir` 后用 `npx asar list` 核对**：`core/app/index.html`、`core/app/shell/app.mjs` 在，`core/.git` 不在。

## 4. 第 3 题：版本号怎么对齐

**规则（五条，写死再执行）**

1. **核仓 `version` 是唯一的产品版本号**，等于 CHANGELOG 当前段（`CHANGELOG.md` 首行 `## v0.5.0-alpha.21 — 2026-11-02`）。
2. **壳仓 `version` 默认与核仓完全相同**（`0.5.0-alpha.21`）：用户看到的安装包名是 `MotionStudio-${version}-setup.exe`（`package.json:70`），它必须等于产品版本，否则「我装的是哪个版本」立刻失真。
3. **壳仓单独修 bug**：`version` 记 `<核版本>.<壳修订>`（如 `0.5.0-alpha.21.1`），壳仓 `CHANGELOG.md` 记一行 `shell.1`，不写回核仓。同一核版本最多三个壳修订，超出就必须发核版本。
4. **tag**：两仓都 `v<version>`；同名不冲突（两个仓库）。
5. **壳仓 bump 核指针时必须同时改 `version`**，或在该提交里显式说明「只 bump 指针、版本不变」。允许「指针前进、版本不变」只限于核仓内部 fix；一旦核仓出了 CHANGELOG 段，壳仓必须跟版本。

**现有版本线已经乱了**（所以规则必须先写死）：`package.json:3` 是 `0.5.0-alpha.21`，而最新 tag 是 **`v1.0.0-beta.1`**；`dist/` 里躺着 `0.0.1-alpha`、`0.0.1-alpha.2`、`0.5.0-alpha.15` 三代安装包（实测）；`tools-pack.mjs:43` 把版本号**硬编码**成 `0.0.1-alpha`，与 `package.json:3` 无关。拆仓时 `tools-pack.mjs` 建议直接弃用（electron-builder 的 nsis 目标已覆盖它）。

**`.msp` 的 `version: 4` 与 `0.5.0-alpha.21` 无关**——两个不同命名空间：

| | 存档格式版本 | 产品版本 |
| --- | --- | --- |
| 写在哪 | 项目文件 JSON 的 `"version": 4`（`README.md:138`、`:141`） | `package.json:3` |
| 谁定义 | `app/shell/project-store.mjs` 的序列化器 | 仓库发布流程 |
| 何时变 | 只有存档结构变化、老档读不进时 | 每次发版 |
| 变了会怎样 | 用户旧 `.msp` 需要迁移代码 | 用户看到新安装包 |

`CHANGELOG.md` 的 v0.5.0-alpha.21 段明写「`.msp` 不升版本（仍是 v4）」。写发版说明时，同一段出现 `v4` 与 `alpha.21` 必须各自加限定词（「存档 v4」「产品 0.5.0-alpha.21」）。

## 5. 第 4 题：七通道契约怎么守

**结论**：契约分两处，各自单仓可跑，再用壳仓的一条测试把两仓缝起来。

1. **核仓**保留 `tests/ipc-contract.test.mjs`，但**瘦身成「核侧快照」**：只断言 `ipc.mjs` 里 `call('name')` 的方法名集合等于七方法白名单，以及 `bridge-web.mjs` 覆盖同一组方法名。它不再读 `preload.js`/`main.js`（拆完那两个文件不在核仓）。

## 6. 第 5 题：网页部署（核仓 README 该怎么说）

核仓 README 的 Browser 段要整段重写：现在的 `README.md:89-93` 说「唯一接触点 `app/shell/ipc.mjs:19`」——实际在 `:51`；说 web bridge「is landing next」——它早已落地（`bridge-web.mjs:249-259`）。`README.md:95-97` 的「Repository split」段从「being moved」改成「已拆」。

可直接粘进核仓 README：

````markdown
### Browser

`app/` **is** the site. Serve that one directory over http(s) and you have the web build —
no build step, no bundler, no server-side code.

```bash
npx --yes serve app -l 8080     # → http://localhost:8080/   (anything static works)
```

Three requirements, all ordinary HTTP rules rather than our quirks:

1. **`.mjs` must be served as JavaScript.** Browsers reject `text/plain` or
   `application/octet-stream` for module scripts; use `text/javascript; charset=utf-8`
   (reference MIME table: the shell's `main.js:14-25`, equivalently `tools-serve.mjs`).
2. **Serve over http(s), not `file://`.** ES modules are fetched with CORS and `file://`
   origins are opaque, so the first `import` fails. Any static host is fine.
3. **CSP stays `default-src 'self'`** (`app/index.html:5`): same-origin modules and
   styles, images as `data:`/`blob:`, no network API calls.

**No Service Worker, on purpose.** There is no offline requirement, nothing is
pre-built to cache (the source *is* the artifact), and a service worker would create a
second invisible version of the app that can drift from the deployed files — it would
also need `worker-src` opened in the CSP above. "Edit a file, reload, see it" is the
whole deploy story.

What the browser build can and cannot do is the web bridge's contract, stated at the
top of `app/shell/bridge-web.mjs`: export goes through downloads, opening files goes
through `<input type=file>`, and "open containing folder" reports that browsers have no
such thing instead of pretending.
````

## 7. 第 6 题：拆分步骤（含窗口期怎么关）

## 9. 执行前的三个待拍板项

**① 核仓到底保不保留 `electron` 这个 devDependency？**
保留 → `package.json` 的 `files` 段与 `tools-smoke.cjs` 的位置稳定、白屏闸门留在核仓，代价是核仓不再是「零开发依赖」，CI 要装 250MB 二进制。

**本文倾向：保留。** 这是唯一必须先定的取舍。

**② 壳仓是「新仓 + 首提交导入」，还是「filter-repo 搬 51 个提交里的壳部分」？**
倾向新仓（第 2 步取舍）：历史读起来更真、维护成本低。若「壳的提交历史」有价值，就要接受 filter-repo 的路径错乱与一次不可逆的历史重写。

**③ 产品标识要不要跟着仓名改？**
`appId` 仍是 `com.satyr.motionstudio`（`package.json:43`）、`productName` 仍是 `MotionStudio`（`:44`）、安装目录仍是 `%LOCALAPPDATA%\Programs\MotionStudio`（`tools-pack.mjs:42`）。
**本文倾向：全都不动。** 仓名（`motionstudio-desktop`）只是开发者组织方式，与用户可见的产品标识无关；动了 `appId` 或产品名，老用户的覆盖升级会变成「装了两个应用」。这条要在壳仓第一次发版前写进 README。
