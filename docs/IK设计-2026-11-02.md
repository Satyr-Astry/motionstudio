# IK（反向动力学）设计——骨骼第三期

> 状态：**步 1–3 已施工**（解算器 `0.5.0-alpha.28`；求值器与蒙皮接缝、`ik` 进存档白名单、属性面板三行 `0.5.0-alpha.29`）。剩步 4 的可选件：极向量、画布上的 IK 目标连线与链高亮。
> 前置：骨骼 P1（`0.5.0-alpha.20`）、P2-A/B/C（`alpha.21`/`alpha.22`/`alpha.24`+`alpha.25`）已发。
> 定位：P3 是骨骼线最后一期功能（P4 是互操作）。本稿给施工级决定，不写代码。

## 0. 一句话结论

**IK 约束挂在链尾骨骼上、目标点是另一个普通对象**，解算用 **CCD**，结果只进渲染矩阵、不回写关键帧；注入点是 `evaluator.mjs` 的 `matrixOfChain` 与 `skin.mjs` 的 `boneWorldMatrix` 两处共同接受的**覆盖表（override map）**，覆盖表由新模块 `app/core/ik.mjs` 单点产出。`.msp` 仍是 `VERSION=4`。

把「目标点」设计成**普通对象**是关键取舍：它立刻可以打关键帧、可以被父链带动、可以复制粘贴，而且不需要给 IK 增加任何新的通道类型或动画 UI —— 等于用既有的 transform 通道免费得到「IK 目标动画」。

## 1. 现状：同一个量目前算了两遍（已是隐患）

骨骼的世界矩阵在代码里有两份独立实现：

| 位置 | 实现 | 谁在用 |
|---|---|---|
| `app/core/evaluator.mjs:306 matrixOfChain(chain,t)` | 工厂闭包内，沿 `chainOf` 自根向叶 `mulMatrix`；每级用 `localTime(el,t)` 与 `sizeOf(el,t)` | `:321 worldMatrix`、`:326 parentMatrix`、`:352 evalLayer` 里的 `const matrix = worldMatrix(layer, tt)` |
| `app/core/skin.mjs:136 boneWorldMatrix(doc,el,t)` | 自己 `chainOf`（`:96`，带 `seen` 防环与 `MAX_DEPTH`）再累乘 `elementMatrix` | `:305 boneMatrices`（蒙皮取骨矩阵的地方） |

`element.mjs` 其实提供了与两者等价的第三套零件：`elementMatrix(el,time,size)`（`:86`）、`elementSize(doc,el,t)`（`:27`）、`anchorPoint`（`:40`）、`mulMatrix`（`:49`）、`invertMatrix`（`:61`）、`applyMatrix`（`:77`）。

**这不是本次要顺手重构的东西**，但它决定了 IK 的实现方式：**不能再加第三份遍历**。IK 只能做「给已有的遍历一张覆盖表」，否则「同一个量算两遍」会在 IK 与蒙皮之间直接长出可见 bug（骨架弯了、皮肤不弯）。

## 2. 注入点：一张覆盖表，两个消费者

```js
// app/core/ik.mjs
/** @returns {Map<string, [a,b,c,d,e,f]>} 骨骼 id → 解算后的世界矩阵（只含被 IK 影响的骨） */
export function solveIk(doc, t) {}
```

调用方规则：

- `evaluator.mjs` 的 `matrixOfChain(chain, t, sol)` 增加第三参：遍历到某个 `el` 时，**若 `sol` 里有 `el.id`，直接令 `m = sol.get(el.id)`**（绝对世界矩阵覆盖累乘值），否则照旧 `m = mulMatrix(m, elementMatrixOf(...))`。`worldMatrix`/`parentMatrix`/`evalLayer` 传同一个 `sol`。
- `skin.mjs` 的 `boneWorldMatrix(doc, el, t, sol)` 同样在累乘前查表；`boneMatrices(doc, skin, t, sol)` 逐骨传入。
- `solveIk` 内部用**单槽缓存**（`doc` 引用 + `t` + 一个修订计数），保证 `evaluator` 与 `skin` 在同帧拿到**同一张表**——这正是 `weight-paint.mjs` 的 `cachedSkinVertices` 已经验证过的做法。

为什么覆盖表而不是「解算后改写 doc」：改写会污染撤销栈、落盘、`sameObjectPixels`，而且用户会看到刚打的关键帧被算法悄悄改掉。

## 3. 求解器选型：CCD

**结论：CCD（循环坐标下降），`iterations` 缺省 8。**

| 方案 | 判定 | 理由 |
|---|---|---|
| 解析法（两骨三边） | 只作特例，不做主路 | 仅 2 骨、且要求「无 skew、等比缩放」。本项目的 `state` 允许 `skewX/skewY` 与非等比 `scaleX/scaleY`（`transform.mjs:22-30`），解析解在这些情况下不成立 |
| FABRIK | 否 | 它在**位置空间**迭代，解完要把位置反解成旋转；反解需要把矩阵分解成 rotate/scale/skew，正是上面说的「不成立」区。而且它不天然保持骨骼长度 |
| **CCD** | **是** | 直接在**世界旋转**上迭代：对关节 i，求 `(末端 − P_i)` 与 `(目标 − P_i)` 的夹角 θ，令世界增量 `D = T(P_i)·R(θ)·T(−P_i)`，则 `M_i' = D·M_i`，子骨依次左乘同一个 `D`。全程只用 `mulMatrix`/`invertMatrix`/`applyMatrix`/`atan2`，不分解矩阵 |

CCD 的已知代价与对策：

- **收敛慢**（每轮只修一个关节）→ `iterations` 缺省 8、`chain ≤ 8`；链更长时解算质量下降而不是发散，可以接受。
- **会「卷」**（缺乏极向量约束时肘部可能翻到另一边）→ MVP 不提供极向量，但 CCD 从当前姿态起步、每轮只转最小角度，所以**保持上一帧的姿态**天然抑制翻转。文档要在 README 里写清「没有极向量」。
- **目标不可达**（目标比链总长还远）→ CCD 自然收敛到「伸直」，这是期望行为，不需要特判；但要有测试钉住「不抛错、不产生 NaN」。

### 3.1 施工时撞到的两个真问题（步 1 已修，写进实现注释）

1. **单轮步长必须夹住**（`IK_MAX_STEP = 0.35` rad ≈ 20°）。不夹的话 CCD 有一个经典卡死：末端关节会「一步转到位」，把两骨链直接折回到根上（追一个比链长短的目标时，末端骨一次转 180°，末端正好落在父关节的位置上）。此后父关节的「关节→末端」向量长度变成 0，**任何旋转都不改变末端位置**，迭代再多也出不来。测试里的「两骨可达」用例就是这个形状，不夹步长时偏差稳定在 100px。
2. **退化方向要有兜底**。即使夹了步长，仍可能碰到「末端与关节重合」的瞬间。原实现直接 `continue`，结果链会卡在折叠姿态；现在改用**骨骼自己的 +x 轴**（世界矩阵的第一列）当参考方向，于是角度仍有定义、下一轮就能转出去。

这两条都只出现在「迭代式求解器」里，解析解不会遇到 —— 这也是选 CCD 要付的学费，记在这里免得下一个人再踩。

## 4. 数据模型

```js
// 挂在**链尾骨骼**上（effector）。链 = 从 effector 沿 parentId 上溯 chain 级。
ik: {
  targetId: 'obj-3',   // 目标对象的 id；缺省/无效 = 不启用
  chain: 2,            // 参与解算的骨数（1..IK_MAX_CHAIN=8），缺省 2
  iterations: 8,       // 1..32，缺省 8
  enabled: true,       // 缺省 true（有合法 targetId 才真正生效）
}
```

- **落盘**：`ik` 是纯数据，进 `project-store.mjs` 的两处白名单（`elementToJSON` / `elementShell`）+ `doc-model.mjs` 的 `makeObject` 原样挂载（与 `skin` 同一套「边界归一、构造器只搬运」的做法）。新增 `normalizeIk(v)` 放在 `doc-model.mjs`（与 `normalizeBone` 并列，`:80`）。
- **不落盘**：解算结果（覆盖表）是每帧派生值，绝不进 doc。
- **`.msp` 版本**：仍是 **4**（`project-store.mjs:54`）。理由与骨骼、蒙皮一致：纯增量字段，旧读入器的白名单会丢弃未知键，不需要迁移。`project-store.mjs` 顶部「故意不升」的注释要补一句 `ik`。
- 为什么不是「单独的 IK 对象」：那会多一种对象类型、多一套命中/选中/面板分支，而收益只是「一个对象上能挂多条 IK」。MVP 不需要。

## 5. 与时间通道、与蒙皮的关系

**时间**：目标对象走它自己的 transform 通道与父链，`solveIk` 内部一律用 `localTimeOf(doc, el, tGlobal)`（`timegraph.mjs:218`）求每根骨的局部时间——与 `matrixOfChain` 的 `localTime`（`evaluator.mjs:207` 一带）口径一致。因此「给目标对象打关键帧」= 「动画 IK 目标」，不需要任何新通道。

**顺序**（必须钉死）：

```
1. 运动学：按关键帧算出所有对象（含骨骼）的世界矩阵        ← 现有 matrixOfChain
2. IK：solveIk 读第 1 步结果，用 CCD 产出覆盖表            ← 新增
3. 蒙皮：boneMatrices 读覆盖表 → applySkin                ← 现有，加一个可选参数
4. 绘制：evalLayer 用覆盖表算 matrix/lattice              ← 现有，传 sol
```

失败模式：若蒙皮读不到覆盖表（少传一个参数），表现是**骨架弯了、皮肤不弯**。这是本批最容易漏的一处，**必须有测试断言「同一帧里 evaluator 与 skin 拿到同一张表」**。

**谁能覆盖谁**：链上骨骼的 `rotate` 关键帧在 IK 生效时被**覆盖**（不写回）。用户若想让某根骨既受 IK 又受关键帧，只能把 `chain` 缩短到那根骨之下。这条要写进面板提示，否则会被当 bug 报。

## 6. UI 最小面

MVP 只加**属性面板骨骼段的三行**（`prop-object.mjs` 现有 `props.obj.groupBone` 组内）：

1. 复选框「IK」（`ik.enabled`）；
2. 目标下拉（列出所有 `kind !== 'bone'` 或所有可见对象；空选项 = 无目标）；
3. 链长数字（1..8）。

**不加画布叠加层**也能用：拖目标对象就是拖 IK。第二步再加「目标连线 + 链上高亮」（与权重态的 `drawBones` 着色同一套写法）。

**不加 UI 也能先验证**：直接给 doc 塞 `ik` 字段即可跑单测——这就是 step 1 的验收方式。

## 7. 可断言的验收（≥8 条，前 3 条是硬门）

1. **单骨 180°**：一根骨 + 目标在根的另一侧同一距离 → 解算后末端世界坐标与目标差 `< 1e-6`。
2. **两骨可达**：目标在可达范围内 → 解算后末端与目标差 `< 1e-3`（迭代上限内收敛）。
3. **不可达退化**：目标距离 > 链总长 → 末端落在「伸直方向」上，**不抛错、矩阵无 NaN**（`Number.isFinite` 逐项检查）。
4. **`chain` 边界**：`chain=1` 只转 effector 自己；`chain` 超过实际父链长度 → 取到根为止，不越界。
5. **目标在链内**（自引用）：`targetId` 指向链上某一根骨 → 必须**拒绝解算**（返回空表），不能死循环。
6. **覆盖表口径一致**：`evaluator` 的 `worldMatrix(bone,t)` 与 `skin.boneWorldMatrix(doc,bone,t)` 在 IK 生效时**逐项相等**（< 1e-9）。这条防「骨架弯了皮肤不弯」。
7. **不影响无关对象**：没有 `ik` 的骨骼、以及所有非骨骼对象，世界矩阵在开关 IK 前后**逐项相等**。
8. **不落盘**：`docToFile` 出来的 JSON 里 `ik` 只有 `{targetId, chain, iterations, enabled}` 四个键；解算结果一个字节都不进档。
9. **`normalizeIk` 夹取**：`chain=0` → 1，`chain=99` → 8，`iterations=0` → 1，坏 `targetId`（非字符串）→ 删掉。
10. **撤销栈干净**：解算前后 `history` 长度不变（IK 不进撤销）。

## 8. 风险清单

1. **目标在链内 / 目标依赖 effector**（例如目标挂在 effector 子树上）→ 每帧目标被自己推着跑，表现为抖动或发散。**必须有环检测**：若 `targetId` 在当前链的祖先或自身，直接不解算（验收 5）。
2. **性能**：每帧每链 `O(chain × iterations)` 次矩阵乘。8 骨 × 8 轮 = 64 次，单链可忽略；但 `solveIk` 若在 `evalLayer` 里被逐层调用就会翻倍——所以必须**每帧一次 + 单槽缓存**。
3. **关键帧被覆盖的错觉**：面板显示 rotate 关键帧值、画布显示解算后的姿态。必须在面板上给出「IK 驱动中」标识，否则用户会以为关键帧失效。
4. **局部时间叠加**：`chain` 上某根骨带时间通道（缩放/循环）时，IK 在**该骨自己的局部时间**下解算，目标却在全局时间下取位置——两者不同步时会出现「追不上」。MVP 的做法是照现状（各用各的局部时间），文档写明限制。
5. **截断链与蒙皮绑定不一致**：`skin.bones[].bind` 存的是**绑定时刻的世界矩阵快照**（`skin.mjs:19` 注释）。IK 改了当前世界矩阵后，蒙皮按 `M_now·B⁻¹` 自动跟随，这条天然成立；但如果用户改了 `chain` 或换目标，绑定姿态不重建，会出现整体偏移。属于用户操作可恢复（重新绑一次），文档提示即可。
6. **`.msp` 兼容**：旧档没有 `ik` → 缺省「无约束」，行为零变化；新档给旧版读会丢 `ik`（白名单丢弃），这是既有语义，不算回归。
7. **`sameObjectPixels` 的连带**：IK 解算结果不落 doc，所以 `pixelsDiffer` 看不到它——这是对的（同一 doc + 同一 t 必然算出同一结果）。但**时间轴拖动时**必须触发重绘；现有 `scheduleRender` 已由时间变化驱动，不需要额外接线。**未实测**：若只改目标对象的 `visible`/`opacity`（不改矩阵），IK 结果不变，符合预期。
8. **P4 的连带**：导出「每骨每帧矩阵」时必须用**解算后**的矩阵，否则导出结果与画面不一致。写进 P4 的前置条件。
