# 网格拖拽：在图像内部拖 = 推附近格点（2026-10）

对应任务 `task-41`。目标手感一句话：**网格编辑模式下，指针落在图像内部但不在格点上时，
拖动不再搬走整块图，而是把附近几个格点一起推出去**——与 Klecks 的 `transform/ffd.ts`
一致；落在格点上仍只动那一个格点；不在网格模式时拖内部仍是移动对象。

## 一、三档优先级

| 命中 | 条件 | 按下后拖什么 | 代码 |
| --- | --- | --- | --- |
| `vertex` | 落在网格顶点（`pickHandle` 返回 `kind:'lattice'`） | 只动这一个顶点，标签「变换」 | `editors/canvas-input.mjs:371` 之前的分支 |
| `soft` | 网格模式（`sel.mode === 'warp'`）+ 指针在图像内部 + 不在顶点上 | 推附近格点，标签「格点变形」 | `editors/canvas-input.mjs:93-124`、`:203-221` |
| `move` | 其余（含非网格模式拖内部） | 移动整个对象（原有行为） | `core/gizmo.mjs` 的 `dragPatch` |

判定顺序放在 `hitAt` 之后、`startDrag` 之前：`pickHandle` 已经先扫过顶点与手柄，
所以「顶点优先」天然成立；锚点仍由 `pickAnchor` 先判（锚点默认压在对象左上角，
和 `v0` 顶点同位置——这是既有行为，本次不动）。

## 二、数学：Klecks 的 FFD 权重 + 按格数算的影响半径

`core/warp-drag.mjs` 逐项移植 `E:\dev\klecks\src\app\script\klecks\transform\ffd.ts`
的 `warpLatticeViaPoint`（`:317-393`）：

- 权重：`w(c,r) = bernstein(cols,c,u) · bernstein(rows,r,v)`，`bernstein(n,k,t) = C(n,k)(1-t)^(n-k)t^k`（同 `ffd.ts:62-65`）。
- 强度：`strength = max(0, 1 - dist)`；`dist` 是**按每轴半径归一化**的距离
  `hypot((sv-u)/ru, (tv-v)/rv)`。
- 边缘衰减：`|sv-0.5| > |u-0.5| || |tv-0.5| > |v-0.5|` 时 `strength *= 0.5`（同 `ffd.ts` 的 `edgeFalloff`），鼓包因此偏向拖动点那一侧。
- 归一：`alpha = (w / Σ w²·strength) · strength`。

唯一偏离 Klecks 的地方是半径。Klecks 用「整块补丁的比例」`influenceRadius = 1/3`，
因为它的网格固定 5×5 个控制点（`kl-app-select.ts` 的 `n(5, 5, ...)`）= 4×4 格，
1/3 补丁约等于 1.33 格。我们的网格密度由用户决定（1×1…12×12，`core/lattice.mjs` 的 `MAX_DIV`），
若也按补丁比例算：**1×1 网格半径只有 0.33 格，而四角离中心 0.707 格 —— 在正中心拖，
一个顶点都够不到，也就是「拖了完全不动」。** 实测纯移植版正是这个结果（`sumWeightsSq = 0`）。

所以半径改成**按格数**算，并给一个下限：`ru = max(1/3, 1/cols)`、`rv = max(1/3, 1/rows)`
（每轴单独取，非等比网格如 3×9 两侧也够得到）。下限 1 格恰好让 1×1 网格的中心拖拽够到四角。

## 三、`1/J` 一次归一即精确

`core/lattice.mjs` 的 `latticeOffset(lat,u,v)` 对顶点是**线性**的（cell 内双线性，
权重只依赖 `(u,v)`），而 `Σ_k W_k = 1`（双线性的四条权重和为 1）。于是把所有权重乘以
同一个 `Δ` 后，`(u,v)` 处的实际位移正好是 `J·Δ`，其中 `J = Σ_k W_k·α_k`。
除以 `J` 之后拖动点**严格跟手**，一次除法闭合，不需要迭代。

`J` 用解析式算（`warpGain`，只取所在 cell 的四角），`err` 则用导出的 `latticeOffset`
**重算**而不信中间量——`tests/warp-drag.test.mjs` 对 1×1 / 2×3 / 4×4 / 12×12 × 6 个位置
断言 `err < 1e-9`，实测 ≤ 7.1e-15。

## 四、撤销：一次拖动严格一条

逐帧写文档**但不进撤销栈**（`ctx.setDoc(next, { silent: true, label: '格点变形' })`，
`editors/canvas-input.mjs:217`），松手时补一条命令：

```js
ctx.engine.pushCommand({
    label: '格点变形',
    undo: () => ctx.setDoc(before, { silent: true }),
    redo: () => ctx.setDoc(after, { silent: true }),
});
```

为什么不用 `setDoc(..., { coalesce })`：显式合并窗口是 `DOC_MERGE_MS = 700ms`
（`app/shell/doc-state.mjs:263`），慢拖中途停一下就断成两三条，与「一次拖动一条撤销」冲突。
静默逐帧 + 松手一条不依赖任何时间窗。

`Esc` 取消：静默把文档回落到按下时那一版，**不推命令**，撤销栈与重做栈都不留痕迹
（`editors/canvas-input.mjs:283-291`）。不用 `ctx.undo()`，因为「先写、再撤销」会在重做栈
留一条用户没做过的记录。

拖动中提示条显示受影响顶点数（只在数字变化时报一次，不刷屏）：
`格点变形：影响 4 个顶点`；松手后显示 `已变形网格`，取消时 `已取消`。

### 与任务书签名的差异

任务书写的是 `hitInside(lat, u, v)` 与 `zoneOf(lat, u, v, radiusPx)`，实现改成
`hitInside(u, v, opts)` 与 `zoneOf(hit, opts)`：内部判定只跟 `(u,v)` 有关、不需要网格；
「当前是不是网格编辑」在选中态里（`sel.mode`），不需要每次传半径。语义不变，语义断言在
`tests/warp-drag.test.mjs` 里覆盖全分支。

## 五、边界：`t ≈ 0` 且对象已有 ≥2 个关键帧

`ensureWarpBaseKey`（`editors/canvas-input.mjs:140-152`）在「当前时间 ≈ 0」或「对象只剩一个关键帧」
时不做任何事——这两种情况当前帧本身就是基准，插不进更早的帧。软拖沿用同一策略：直接在
`t = 0` 写这一帧的 warp。理由：warp 与 x/y/旋转存在**同一个** transform 轨道的关键帧里，
t=0 已有键时它已经是整条轨道的起点，再补键只会改动别的时刻的求值结果。

## 六、影响范围圈

拖动中在参数空间按椭圆采样（64 段）再走 `lat.map → toScreenArr`，因此**跟随旋转与已发生的形变**，
画在 `editors/canvas.mjs` 的 warp 叠加层里（`previewSoftDrag()`）。采样点先夹到 `[0,1]²`
（`canvas.mjs` 的 `clamp01`）：圈外的参数空间没有几何可影响，画到对象外面只会误导——
1×1 网格时半径就是 1 格，未夹取会画出一个比对象大一圈的椭圆。

## 九、已知限制

- 1×1 网格（默认）只有四个格点，软拖等价于把整块图平移——这是四点网格的数学上限，
  不是 bug。要局部形变请在网格模式下先加细分（`MAX_DIV = 12`）。
- 顶点与锚点同位置时锚点优先（`pickAnchor` 先判），这是既有行为，本次未改。
- 3D 曲面、`paint/composite.mjs` 的渲染路径未动：warp 仍走原来的 `latticePoint` 采样。
- 软拖的基准是**按下时那一版网格**，所以拖动中对同一处反复来回不会累积漂移。
